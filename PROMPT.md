# Nix tools hardening handoff

Take ownership of the next hardening phase of this `nix-tools` repository. Implement the work—do not stop at a plan. The public APIs are unpublished and may change when a cleaner design is justified.

Before changing anything, read `AGENTS.md`, `README.md`, `docs/`, the Rust crates, Nix libraries, examples, tests, and CI workflow. Establish the current verification and benchmark baseline. The Bun source code is available at `../bun`; inspect it read-only as the authoritative local reference for lockfile, installer, global-cache, lifecycle, workspace, and resolution behavior. Use current official Bun and Nix documentation/source where behavior cannot be proven locally.

Use `$tdd-workflow`, `$verification-loop`, `$documentation-lookup`, and `$strategic-compact` where relevant.

## Priorities

### 1. Harden `bun2nix` compatibility and correctness

- Build a representative lockfile corpus covering every dependency/source form supported by the pinned Bun release: registry packages, aliases, scoped packages, workspaces, file/tarball dependencies, git sources, private registries, optional and peer dependencies, platform restrictions, overrides/resolutions, patches, catalogs, trusted dependencies, lifecycle scripts, and native packages.
- Prefer fixtures generated by Bun or extracted from attributable public repositories over hand-invented approximations.
- Differential-test parsing, dependency closures, cache-entry names, offline installation, and resulting workspace trees against Bun itself.
- Unsupported semantics must fail with an actionable error rather than silently generating incorrect Nix.
- Separate production, check/test, and development dependency closures. Production caches and builds must not include dev-only dependencies.
- Preserve exact workspace-consumer sharing and deterministic `bun.nix` generation.
- Model lifecycle scripts as an explicit trust boundary; they remain disabled unless callers deliberately opt in.

### 2. Measure and improve monorepo performance

- Add a reproducible benchmark harness for evaluation, graph construction, cache probing, realization, and no-op rebuilds.
- Cover increasing workspace/target counts and shared versus workspace-exclusive dependencies.
- Record wall time, process count, peak retained output/memory where practical, derivation count, cache reuse, and invalidation fan-out.
- Compare the current implementation with plain Nix and `nix-fast-build` where available.
- Profile before optimizing. Only implement changes supported by measurements.
- Investigate incremental discovery/evaluation state for repeated `check`, `build`, and `run` calls. Add persistent state or a daemon only if measurements show it materially helps without weakening correctness.
- Document baseline and resulting measurements in `docs/benchmarks.md`; do not commit machine-specific build artifacts.

### 3. Prove binary-cache interoperability

- Compare generated NARs, hashes, references, narinfo records, and signatures against Nix's own tooling using temporary fixtures and keys.
- Add integration tests for files, directories, executable bits, empty directories, symlinks, dangling symlinks, reference graphs, corruption, cancellation, and partial publication failure.
- Ensure concurrent CI units publish only paths they own and cannot publish dependants before prerequisites settle.
- Keep credentials, storage providers, compression policy, retention, and trust roots outside the core. Add concrete adapters only where they validate the existing abstraction without pulling provider policy into the reusable crates.

### 4. Pressure-test reuse

- Inspect `../atlas`, `../flutter2nix`, `../jfit`, and the original `../tools` read-only to identify real selectors, mixed-language outputs, nested flakes, and repository-specific subcommands the API must accommodate.
- Do not modify those repositories.
- Represent the important integration patterns through fixtures or examples inside this repository.
- Keep `nix-tools` as a thin reference CLI. Repository CLIs must be able to compose the engine and command services while owning their arguments, selectors, rendering, and additional commands.

## Constraints

- Work only in this repository. Do not modify sibling repositories.
- Treat `../bun` as a read-only reference; do not modify it.
- Do not introduce Buildkite-specific crates or configuration. CI remains GitHub Actions on Blacksmith.
- Do not create a GitHub Actions-specific Rust crate; provider-specific workflow YAML belongs under `.github/workflows`.
- Do not perform broad searches over `/nix/store`; use exact store paths and bounded Nix queries.
- Preserve the ordinary-attrset Nix API and the separation between reusable mechanics and repository/provider policy unless evidence supports a better boundary.
- Keep dependencies minimal and justify any new dependency.
- Never weaken validation, tests, cache trust, cancellation, or reproducibility for performance.
- Use `jj`, make one conventional local commit per logical phase, and do not push.

## Verification

- `cargo fmt --all --check`
- `cargo check --workspace --all-targets`
- `cargo clippy --workspace --all-targets -- -D warnings`
- `cargo test --workspace`
- Root `nix flake check`
- `nix flake check` for the Bun monorepo example
- Frozen offline Bun installs, tests, and builds
- Real `nix-tools check`, `build`, and `run` smoke tests
- Deterministic regeneration checks for `bun.nix`
- New differential, interoperability, and performance tests
- A final review of the complete diff for correctness, security boundaries, missed edge cases, and unintended changes

Completion means the supported Bun behavior is explicitly tested or explicitly rejected, production closures exclude dev-only dependencies, cache output interoperates with Nix, benchmarks demonstrate the effects of performance changes, all verification passes, documentation matches the implemented behavior, and the working copy is committed locally and clean.

In the final response, report the behavior changed, exact test totals and benchmark results, local commits created, remaining known limitations, and confirmation that no sibling repository or remote was modified.
